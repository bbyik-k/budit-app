## 1. `normalizeName()` 정규식과 반환값

### 코드 원문

`lib/ingredients/normalize.ts:7-12`

```ts
export function normalizeName(raw: string): string {
  return raw
    .replace(/[\(\[\{][\d.\s]*%?\s*[\)\]\}]/g, "") // :9
    .replace(/\s+/g, " ") // :10
    .trim(); // :11
}
```

정규식은 `:9`의 `/[\(\[\{][\d.\s]*%?\s*[\)\]\}]/g` 하나다. `:10`은 연속 공백 축약, `:11`은 앞뒤 공백 제거.

### 반환값 (`node -e` 실행 검증)

| 입력                     | 반환값                | 괄호 제거                 |
| ------------------------ | --------------------- | ------------------------- |
| `"레티놀"`               | `"레티놀"`            | —                         |
| `"레티놀(500IU/g)"`      | `"레티놀(500IU/g)"`   | ✗                         |
| `"레티놀 (500IU/g)"`     | `"레티놀 (500IU/g)"`  | ✗ (괄호 앞 공백도 그대로) |
| `"나이아신아마이드(2%)"` | `"나이아신아마이드"`  | ✓                         |
| `"토코페롤(비타민E)"`    | `"토코페롤(비타민E)"` | ✗                         |
| `"정제수(물)"`           | `"정제수(물)"`        | ✗                         |

### 판정 근거

`[\d.\s]*%?`가 괄호 안 내용을 **숫자·점·공백·%로만** 제한한다. 따라서:

- `(2%)` — `[\d.\s]*`가 `2`, `%?`가 `%`, 닫는 괄호 매칭 → **제거됨**
- `(500IU/g)` — `[\d.\s]*`가 `500`까지 먹은 뒤 `I`를 만나 실패. 백트래킹해도 `%` 또는 닫는 괄호가 나와야 하므로 전부 실패 → **미제거**
- `(비타민E)`, `(물)` — 첫 문자부터 문자 클래스에 없음 → **미제거**

괄호 앞 공백은 정규식과 무관하다. `:10`이 이미 단일 공백인 것을 그대로 두고, `:11`의 `.trim()`은 문자열 앞뒤만 처리하므로 중간 공백은 보존된다.

이 결과는 `docs/INGREDIENT_MATCHING.md:37`의 기존 기록과 일치한다.

## 3. 계획서의 "확인 불가" 3건 — 전부 해소

| 항목                                           | 실측 결과                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `RETURNS TABLE` 9컬럼과 실제 반환 키 일치 여부 | **일치.** 반환 키가 정확히 `ingredient_a, ingredient_b, a_type, b_type, conflict_type, severity, reason_ko, recommend, source` 9개. `id`/`created_at`/`updated_at`은 오지 않음 |

| `source` 실제 값                               | **`null`**                                                                                                                                                                     |

→ 6번 zod 스키마에서 `severity` · `recommend` · `source`는 `.nullable()`, `"" → null` 전처리는 불필요.

## 4. 추가 발견 — synergy 행의 컬럼 밀림 (6번 스키마에 영향)

`conflict_rules`의 synergy 행은 **`reason_ko`가 빈 문자열 `""`이고, 설명 텍스트가 `recommend` 컬럼에 들어가 있으며, `source`는 `null`**이다.

```json
{
  "conflict_type": "synergy",
  "severity": null,
  "reason_ko": "",
  "recommend": "히알루론산(수분 공급·흡착)과 세라마이드(장벽 강화·수분 잠금)의 완벽한 보습 시너지. 수분 채우고 잠그는 이상적인 조합.",
  "source": null
}
```

**원인:** `data/csv/conflict_rules.csv`의 필드 수 불일치. 헤더는 9필드(`ingredient_a, ingredient_b, a_type, b_type, conflict_type, severity, reason_ko, recommend, source`)인데 synergy 행은 10필드다.

```
# :38 — 필드 10개 (빈 필드가 하나 더 있음)
레티놀 계열,보습제 계열,group,group,synergy,,,"글리세린·히알루론산 등 보습제가 …",,Paula's Choice
#                                          ^^ severity 빈칸, reason_ko 빈칸
#                                              → 설명이 recommend로 밀림
#                                              → source 유실, 10번째 필드는 버려짐
```

**영향 2건:**

1. **6번 스키마** — `reason_ko`는 반드시 `z.string()` (min 없음)이어야 한다. `.min(1)`을 걸면 synergy 행이 전부 검증 실패하고, throw 정책상 분석 전체가 500이 된다.
2. **현재 UI** — `lib/analyze/conflict.ts:37`이 `reasonKo: r.reason_ko`로 매핑하므로 **시너지 설명이 화면에 빈칸으로 렌더된다.**

데이터 자체 수정(CSV 필드 정정 + 재시드)은 이번 1~6번 작업 범위 밖이므로 건드리지 않았다.
